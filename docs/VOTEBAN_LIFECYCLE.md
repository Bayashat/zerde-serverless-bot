# Voteban lifecycle and recovery

Status: **IMPLEMENTED_UNPROVEN**. Local SDK/Moto tests establish the state transitions below; they do not establish deployment, real Telegram behavior, or production acceptance. No cloud resources, Telegram messages, vote thresholds, member permissions, or configured ordinary temporary-ban duration were changed by this implementation.

## Authority and identities

`VoteRepository` owns the existing stats-table key `voteban_<chat_id>_<target_user_id>`. There is one current row for each chat/target pair, not a second moderation store. The row records schema version 2, a random generation, a revision, the initiating command and highest observed command message IDs, the exact published vote message ID, the original target message ID, and the command chat type. Stored names are only the same display metadata already used by this feature; no chat text is copied into the row.

A command conditionally creates `CREATING`, with the initiator's original vote. A concurrent command reuses that generation and preserves all existing votes. Commands reused while the session is active also advance the conditional command watermark: replaying one after completion cannot reopen the vote. A genuinely newer command can start a new generation only after the previous vote has expired or its terminal effects have completed. Command dates older than 24 hours (or more than five minutes in the future) are rejected; this prevents an old command from recreating a vote after its receipt was physically removed.

The first message has no clickable keyboard. Only after a conditional update binds its returned message ID does the handler install buttons. A lost send response or failed binding can leave an inert message; retrying the command can publish another inert message and then bind it. It cannot publish an actionable orphan. `CREATING` expires after three hours; after a crashed invocation's lease has expired, the same command can resume, or a newer command can replace an expired generation. There is no claim of exactly-once message delivery.

Buttons carry `target_user_id:generation` and retain the existing dispatcher prefixes. A callback must match its chat, target, generation, and exact stored vote message ID. Legacy buttons without a generation are safely rejected; they never attach to a replacement session. Existing legacy rows remain untouched until their old TTL deadline; a legacy row with no valid deadline requires explicit operator inspection. Rollout does not import old votes into the new schema.

## Decisions and effects

| State | Allowed progress |
| --- | --- |
| `CREATING` | Bind the inert message, then `OPEN`; if the existing configured ban threshold is one, binding decides `BAN_PENDING` immediately. |
| `OPEN` | One vote per user across both choices; strong read plus revision CAS accepts only a still-open, unexpired row. |
| `BAN_PENDING` / `FORGIVE_PENDING` | The first threshold-crossing vote and decision are one conditional write. Opposite votes cannot reverse the decision. Repeated callbacks, including an already-recorded voter's callback, resume effects. |
| `BANNED` | Telegram explicitly returned `ok: true, result: true`; setting this state and incrementing `total_bans` are one native-value DynamoDB transaction. A duplicate transaction cannot count again. |
| `FORGIVEN` | The forgiveness decision is durable before announcement or cleanup. |
| `UNCONFIRMED` | The execution window expired, membership changed, or configured duration would risk a permanent ban. No ban is counted. The public notice asks an administrator to check the result; a new decision requires a new command. |

All external effects share one 360-second session lease. Votes can continue through revision CAS while a keyboard edit is in progress. The lease holder rereads after editing and handles a newly decided outcome before releasing; a competing effect invocation reports retryable contention. A bounded render pass can ask the user to retry during sustained concurrent changes. It does not discard accepted votes or claim a pending decision is complete. Terminal cleanup never substitutes an incoming callback's message ID for the stored identities.

Temporary bans execute only for stored `supergroup` chat type. Telegram ignores `until_date` for basic groups, so basic/unknown chat types produce `UNCONFIRMED` without sending a ban. Voting and forgiveness retain their existing participation rules. Temporary bans use the existing effective duration (at least 60 seconds, from Z13), with one `ban_until` written just before the first API attempt. Retries use that same deadline. No API attempt occurs with 40 seconds or less remaining, and the shared Telegram adapter disables implicit HTTP retries for moderation. A decision first executed after the three-hour session deadline is also left unconfirmed. Configurations longer than 365 days fail closed because Telegram interprets dates beyond 366 days as permanent bans; this guard does not silently choose a new duration. There remains an unavoidable transport/clock uncertainty window; local tests are not a Telegram delivery guarantee. These guards follow the official [Telegram banChatMember contract](https://core.telegram.org/bots/api#banchatmember), checked during implementation.

Membership is checked again at execution. An administrator, creator or already-banned member is not banned or counted by this vote. A missing/failed membership read is retryable, not evidence of an ordinary member. If a successful Telegram call loses its response, or the database write fails afterward, subsequent `kicked` membership is reported as unconfirmed: it cannot prove whether this vote or another moderator caused the ban. This can undercount a real ban; it cannot falsely attribute or double-count it. No compensating unban is issued, and an uncertain expired deadline never starts another 60 seconds.

Terminal state is saved before sending a notice. Notice ID, vote-message deletion, and (only after a confirmed ban) original-target-message deletion are recorded separately. A failed notice or cleanup remains recoverable through the same callback or `/voteban` against the same target. Deleting a message already deleted is accepted only through the Telegram adapter's structured not-found classification; other failures do not mark completion. An acknowledged send followed by a failed database update may duplicate the notice on retry. Completed outcomes perform no more Telegram effects.

## Expiry and recovery limits

- The voting window is three hours, enforced in every conditional vote update regardless of asynchronous DynamoDB TTL removal.
- Open/creating rows and completed terminal receipts have a seven-day physical TTL. Once a decision is pending, its TTL is removed until terminal notice/cleanup completes, so an outage does not silently erase unfinished work.
- Recovery is request-driven: repeat a valid button or issue `/voteban` against the same target. There is no new scheduler, queue, background scan, or promise of autonomous recovery in Z14. After a crash, wait for the 360-second lease to expire before retrying. An unexpired pending or incomplete terminal result is resumed rather than overwritten by a new command.
- If the vote message was manually removed while still `OPEN`, its old callbacks cannot be trusted for a replacement message. Wait for the three-hour logical expiry and issue a new command; this implementation does not rebind an active vote to arbitrary messages.
- If Telegram permissions or its deletion time limit prevents terminal cleanup, an administrator must fix permissions or remove the exact stored message and retry the command. Do not delete/reset the row to bypass an unresolved outcome. An indefinitely unresolved decision retains its small metadata row until explicitly recovered.
- The seven-day TTL is a bounded receipt window, not a historical audit ledger. Callback generation matching and the 24-hour command-date gate protect replay after physical cleanup. A new command ID is required for a genuinely new vote.

## Rollout, rollback and acceptance

1. Integrate with the Z13 Telegram adapter that verifies moderation success and disables implicit moderation retries, plus Z02 safe logging. Do not deploy this handler against an older adapter; its return value could otherwise be mistaken for confirmation.
2. Before replacing old writers, stop admission of vote commands and callbacks at the shared entry point. Read the **actual deployed** invocation timeouts for all functions that can run those handlers, and wait for those invocations to drain. The source Bot timeout is 300 seconds; the 360-second lease is valid only while every deployed writer timeout is shorter. If any writer timeout is 360 seconds or longer, stop and revise the lease before activation. The new CAS rules cannot fence an already-running old unconditional writer.
3. Inspect only lifecycle metadata of existing vote rows. Old generationless buttons must be rejected after cutover. Do not delete stats rows or alter `total_bans`, contests, captcha or spam state as part of rollout.
4. Run `uv run pytest tests/test_voteban.py -q`, the complete test suite and pre-commit. The focused tests use actual boto3 Resource serialization plus Moto, with synthetic Telegram responses; they include controlled stale-read interleavings rather than claiming distributed AWS concurrency validation.
5. After separately authorized deployment, read back the artifact, adapter version and timeouts. In a designated test group, validate two concurrent commands, old and wrong-message buttons, both threshold races, replay after completion, and injected Telegram/database failures. Confirm temporary duration and membership with Telegram, and verify the exact `total_bans` delta. Do not manufacture real group bans as an unattended canary.
6. If acceptance fails, stop vote admission and drain writers again. Preserve the schema-2 rows and receipts. Rolling back to the unconditional legacy writer while buttons or pending outcomes exist is unsafe; use an inert/disabled voteban path until a forward fix is reviewed. Neither a passing test suite nor a merged PR closes production acceptance.
