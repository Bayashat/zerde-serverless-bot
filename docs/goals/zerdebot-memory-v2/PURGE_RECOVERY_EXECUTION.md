# Z09：删除任务发现与推进优化

Goal / Intent：修复真实群中一次来源删除后台收尾耗时 675 秒的问题，
使新删除任务的发现不再随着无关聊天记录的数量增长。
Plan：已批准 PLAN.md 的 Z09/Z11，issue #166 的 2026-09-21 真实测试反馈。
Truth owner：MemoryLifecycle 的同一 PURGE 行、原 CONTROL/subject/source 围栏和版本。

## 契约与切换

- 复用独立 V2 表现有 KEYS_ONLY `work-due` 索引，使用单独的
  `work_queue=MEMORY_PURGE` 命名空间。新任务与停止写入围栏在原事务中保存
  `due_at=created_at`；完成时在原事务中移除索引字段。
- 索引只给出待办提示；每次强读原 PURGE，再由原 `advance` 检查身份、epoch、
  revision、在途租约和保留类型。索引延迟、重复或陈旧项不证明可删除或已完成。
- 五分钟恢复规则、20 秒 purge 时间预算保持。索引采用独立持久游标，逐个记录
  已尝试项；失败任务仍待办，并在轮转后重试，不让单个故障或大任务占据队首。
- 每个任务最多推进 20 个原有 40 行页，页间检查本次恢复 deadline；
  源/用户删除仍需遍历本群，数据量带来的实际删除成本不承诺消失。
- 原全表扫描只负责发现并补索引旧未完成任务，保留原持久游标、最多两页。
  该兼容步骤独立限时，不能阻止索引路径；旧任务初次发现仍可能较慢。
  它不再负责逐次清理推进。确认没有旧 writer/未索引任务后可单独退役兼容扫描。
- 不新增表、队列、函数、定时规则、模型调用或 IAM。不更改命令权限、确认时机、
  知识抽取、费用账本、默认学习关闭与旧功能退役边界。

## 验收证据

1. 上千无关行下，新删除一次索引恢复可发现并推进，不靠扫描命中；
   100+ 目标行可在同一次恢复完成，同时不动其他主体/群/业务数据。
2. 老任务补索引、空过滤页、GSI 延迟和陈旧 DONE 项、完成移除索引、
   事务失败、并发 CAS、毒任务与大任务公平性、时间截止后的游标续跑。
3. 原 source/subject/group 隔离、租约、编辑/重复/更正与防复活回归。
4. 部署验收与新的专用测试群自动清理计时单独记录；本地通过不等于真实延迟改善。
